# 宝宝月龄科普功能方案

## 1. 背景

当前 `baby-diary` 已经具备这些核心能力：

- 日常记录：喂奶、睡眠、尿布、用药、体温、黄疸、脐护、洗护
- 成长管理：身高、体重、头围
- 疫苗管理：计划疫苗、自定义疫苗、接种状态
- 家庭协作：多人共同记录

产品已经解决了“记”和“管”的问题，但还没有解决一个高频问题：

> 家长知道要记录，但不一定知道“这个月龄最该关注什么”“为什么会这样”“接下来我可以做什么”。

用户给出的图片内容，正好对应这个缺口：它们不是长篇百科，而是按月龄整理的轻知识清单，和日常照护、成长训练、疫苗、喂养、睡眠高度相关。

因此，这个功能更适合被定义为：

> 一个和记录强联动的“月龄轻科普模块”，而不是独立内容社区。

## 2. 产品目标

### 2.1 要解决的问题

1. 新手父母不知道当前月龄的重点照护事项。
2. 用户记录了很多数据，但缺少“如何理解这些数据”的轻解释。
3. 疫苗、喂养、睡眠、辅食等场景存在知识焦虑，用户需要即时参考，而不是跳出应用外搜。
4. 家庭成员之间缺少一套统一的“本月重点”共识。

### 2.2 目标

- 让用户打开 App 就知道“这个月龄现在该关注什么”
- 让知识内容自然带动记录行为，而不是把用户带离主流程
- 提升首页、疫苗、成长、记录页的停留与回访价值
- 建立产品从“记录工具”向“轻育儿助手”的感知升级

### 2.3 非目标

- 不做文章流、资讯流、社区流
- 不做医疗诊断
- 不在第一期做复杂 AI 问答
- 不在第一期覆盖 0-6 岁全量育儿百科

## 3. 产品定位

建议将该功能定位为：

> 以宝宝当前月龄为中心的“照护提醒 + 发育提示 + 可执行建议 + 风险边界”模块。

它的核心价值不是“知识很多”，而是“当下有用、可信、能立刻行动”。

## 4. 为什么值得做

结合现有产品结构，这个功能和当前系统天然兼容：

- 首页已有宝宝年龄、今日记录、成长、疫苗等强入口，适合承接“本月龄重点”
- 疫苗模块已具备月龄逻辑，适合补充“打什么”和“为什么”
- 成长模块已有数据，适合补充“这个阶段常见表现”
- 记录模块已有喂养/睡眠/黄疸/脐护等类型，适合加入相关提示

换句话说，这个功能不是平地起楼，而是给现有功能加一层“理解层”。

## 5. 方案原则

### 5.1 场景优先

知识必须挂靠在真实照护场景里，例如：

- 喂养
- 睡眠
- 疫苗
- 发育训练
- 辅食
- 安全护理

### 5.2 轻量优先

每个知识单元要短、清楚、可执行，避免长文堆砌。

### 5.3 月龄优先

先按月龄组织，再按专题展开。因为父母最自然的问题通常是：

> “宝宝现在 3 个月了，我这个阶段该注意什么？”

### 5.4 行动优先

每段内容都尽量带一个动作出口，例如：

- 去记录今天睡眠
- 去补一条成长数据
- 查看疫苗计划
- 新增辅食记录

### 5.5 风险保守

所有涉及医学、营养、异常判断的内容必须弱化诊断感，加入明确边界说明。

## 6. 功能结构

建议拆为 3 层。

### 6.1 第一层：首页“本月龄重点卡”

这是第一触点，也是最重要的入口。

建议在首页新增一个模块：

- 标题：`本月龄重点`
- 副标题：如 `3月龄 · 认人、互动、翻身前准备`
- 内容：3-4 条本月重点摘要
- 操作：
  - `查看完整科普`
  - `去记录`

卡片示例：

- 本月可能开始认人，建议多和宝宝说话、做表情互动
- 俯卧抬头和翻身准备可以开始加强
- 如果夜醒频繁，可先结合白天睡眠和喂养节奏观察

### 6.2 第二层：月龄科普详情页

进入后按宝宝当前月龄展示完整内容。

建议信息结构：

1. 本月一句话总结
2. 本月重点关注
3. 喂养与睡眠
4. 发育与互动训练
5. 疫苗 / 营养 / 护理提示
6. 需要留意的异常信号
7. 相关操作入口

建议页面顶部支持切换：

- 当前月龄
- 上一个月龄
- 下一个月龄

这样家长也能提前看“下个月可能会发生什么”。

### 6.3 第三层：场景化知识插片

不要把所有知识都挤到一个页面里，建议在关键页面插入轻提示：

- 疫苗页：接种前后注意事项、为什么这一针重要
- 成长页：当前月龄可能出现的发育表现
- 记录页：例如黄疸、脐护、洗护、睡眠记录的基础说明
- 辅食相关页面未来上线后：添加顺序、观察原则、过敏提示

## 7. MVP 建议

第一期不要做太重，建议只做 `1-6 月龄`，优先覆盖用户现有素材已经对应的内容。

但有一个前提：

> 如果内容生产和复核资源暂时没有准备好，第一版应收缩为 `1-3 月龄`，先把口径与质量打磨稳定，再扩到 6 月龄。

### 7.1 MVP 范围

1. 首页新增 `本月龄重点卡`
2. 新增 `月龄科普详情页`
3. 覆盖 `1-6 月龄` 内容，或在资源不足时先覆盖 `1-3 月龄`
4. 详情页内加入关联操作按钮
5. 多宝宝场景下，基于“当前选中的宝宝”展示对应月龄科普

### 7.2 MVP 不做

- 搜索
- 收藏
- 评论
- 内容订阅
- AI 自由问答
- 后台 CMS
- 医生在线服务
- 分散在多个业务页里的场景插片

### 7.3 为什么这样收

这样做有 3 个好处：

1. 成本低，可以先验证用户是否真的会看
2. 不会把 P1 做成跨多个页面的复杂联动版本
3. 内容量可控，适合先做可信的小而精版本

## 8. 内容模型建议

第一期建议把内容拆成统一结构，方便以后扩展到更多月龄或专题。

每个月龄包含：

- `month`: 月龄
- `title`: 本月主题
- `summary`: 一句话总结
- `highlights`: 本月重点数组
- `feeding_sleep`: 喂养与睡眠建议
- `development`: 发育与互动训练
- `care`: 护理提示
- `vaccines_nutrition`: 疫苗或营养提示
- `red_flags`: 异常留意项
- `actions`: 关联操作入口
- `sources_note`: 内容来源/审核说明
- `updated_at`: 更新时间

这样后续无论做前端静态配置，还是迁移到后端内容表，结构都能复用。

## 9. 内容表达方式建议

为了降低阅读门槛，建议每个月龄内容尽量采用以下表达：

### 9.1 一句话摘要

例如：

- `1月龄：重点是睡眠、黄疸观察、脐带护理和基础安抚`
- `2月龄：常见肠胀气与肠绞痛，建议更多安抚和俯卧练习`
- `3月龄：开始更爱互动，适合强化语言和视觉追踪`

### 9.2 可执行建议

避免只讲概念，尽量落到动作：

- 每天安排 2-3 次短时俯卧
- 多做面对面交流、表情模仿
- 观察夜醒是否与白天小睡碎片化有关

### 9.3 风险提示

例如：

- 如出现持续高热、明显拒奶、精神差等情况，请及时线下就医
- 辅食添加和营养建议仅作一般性参考，个体情况需遵医嘱

## 10. 与现有模块的联动建议

### 10.1 首页

增加一张 `本月龄重点` 卡片，作为科普主入口。

#### 多宝宝展示逻辑建议

`baby-diary` 支持多宝宝，因此首页科普内容不能按“最近有记录的宝宝”自动猜测。

建议规则如下：

1. 默认跟随当前首页正在查看的宝宝上下文
2. 如果产品已有宝宝切换能力，则科普内容随切换同步变化
3. 如果未来支持首页多宝宝聚合展示，也应要求用户先显式选择宝宝，再进入对应科普

原则：

> 科普内容必须绑定明确宝宝，不做隐式推断。

### 10.2 记录页

在特定记录类型中加入 `为什么要记` 和 `本月龄参考`：

- 睡眠：当前月龄典型睡眠节奏说明
- 黄疸：仅提供观察与就医边界，不做诊断
- 脐护：基础护理说明
- 洗护/抚触：频率和注意点

### 10.3 成长页

根据当前月龄展示：

- 本阶段常见能力
- 家长可以做的互动训练
- 与成长记录的关联提示

### 10.4 疫苗页

在现有疫苗记录基础上增加：

- 为什么这个月龄要关注该疫苗
- 接种前后的一般注意事项
- 明确“以当地接种门诊和医生建议为准”

### 10.5 家庭协作

可以让家庭成员看到同一套“本月重点”，降低照护理解偏差。

## 11. 页面方案建议

### 11.1 首页卡片

建议文案结构：

- 标题：`本月龄重点`
- 副标题：`3月龄 · 认人、互动、抬头更稳`
- 内容区：3 条摘要
- 底部按钮：
  - `查看完整内容`
  - `去记录今天`

### 11.2 月龄详情页

建议模块顺序：

1. 页头：月龄标题 + 插画/轻视觉
2. 本月重点
3. 今日最值得做的 3 件事
4. 场景分区：
   - 喂养睡眠
   - 发育互动
   - 疫苗营养
   - 护理注意
5. 异常留意
6. 跳转按钮

### 11.3 场景插片

样式尽量轻，类似信息卡，不要太像“广告位”或“资讯流”。

## 12. 技术落地建议

建议分两阶段做。

### 12.1 第一阶段：轻配置版

目标：最快验证功能价值，同时保留低成本纠错能力。

这一阶段建议优先采用“远程配置驱动、前端渲染”的轻方案，而不是把内容硬编码死在前端包里。

实现方式建议：

- 前端保留统一的月龄内容数据结构
- 内容来源优先读取远程 JSON 配置
- 远程配置可放在现有 Cloudflare 基础设施中，例如 `KV` 或 `R2`
- 前端在成功拉取后缓存最近一次成功内容快照
- 当远程配置不可用时，优先降级为“上一次成功拉取的本地快照”
- 如果本地也没有快照，再降级为随包发布的基础版默认配置
- 依据宝宝出生日期自动计算当前月龄
- 首页读取对应月龄内容摘要
- 新增一个月龄详情页

优点：

- 开发成本仍然较低
- 内容修正不必等待完整发版
- 保留第一期内容快速试错空间
- 与现有 Cloudflare 基础设施匹配
- 远程异常时仍能保持较稳定的用户体验

缺点：

- 仍然需要一套简单的内容发布流程
- 配置版本管理需要约定

#### 推荐的降级链路

建议采用这一条固定链路：

1. 读取远程 JSON 配置
2. 成功则更新前端本地缓存快照
3. 远程失败则读取本地缓存快照
4. 本地缓存不存在时，回退到内置基础版内容

这样可以同时兼顾：

- 日常内容修正效率
- 弱网或接口异常时的稳定性
- 首次安装时的可用性

### 12.2 第一阶段备选：纯前端静态内容版

如果希望把第一版做到最极致简单，也可以退回纯前端静态内容方案。

实现方式建议：

- 在前端本地维护一份月龄内容配置
- 依据宝宝出生日期自动计算当前月龄
- 首页直接读取对应月龄内容摘要
- 新增一个月龄详情页

优点：

- 开发快
- 不改数据库
- 不增加后台系统
- 适合第一版内容打磨

缺点：

- 内容更新要发版
- 运营不可独立维护

是否采用该方案，取决于团队是否能接受：

> 当某条内容表述需要紧急修复时，修复节奏受发版和审核周期影响。

### 12.3 第二阶段：后端内容化

在第一期验证有效后，再考虑：

- 新增 `education_guides` 或类似内容表
- 支持月龄、专题、状态、版本、更新时间
- 后台维护内容
- 后续支持更多专题，如辅食、发热、出牙、安全等

## 13. 数据结构建议

如果未来上后端，建议内容实体大致包含：

- `id`
- `age_start_month`
- `age_end_month`
- `category`
- `title`
- `summary`
- `content_json`
- `medical_disclaimer`
- `review_status`
- `reviewed_by`
- `updated_at`

其中 `content_json` 可承载模块化内容，避免表设计过早复杂化。

## 14. 指标建议

可以重点看以下指标来判断这个功能值不值得继续扩：

### 14.1 使用指标

- 首页 `本月龄重点卡` 曝光率
- 卡片点击率
- 月龄详情页访问人数
- 单用户月均访问次数

### 14.2 联动指标

- 从科普页跳转到记录页的转化率
- 从科普页跳转到疫苗页 / 成长页的转化率
- 有科普触达用户的记录频次变化

### 14.3 感知指标

- 用户是否更容易理解当前阶段重点
- 家庭成员是否更容易形成一致照护动作

## 15. 风险与边界

这是该功能最需要谨慎的部分。

### 15.0 内容生产与维护风险

这其实是第一期最现实的风险点，甚至比开发风险更大。

建议在 P0 阶段明确以下角色：

- 谁负责起草内容
- 谁负责产品口径统一
- 谁负责医学/营养/疫苗相关内容复核
- 谁负责最终上线前确认

如果上述责任没有明确，P1 很容易卡在“功能已经做好，但内容不敢上”的状态。

#### 当前阶段的推荐责任分配

如果当前阶段是独立开发推进，建议直接按下面的最小责任模型执行：

- 内容起草：由你本人负责，先把原始资料整理成产品内短内容
- 产品编辑：仍由你本人负责，统一语气、信息层级、长度和跳转动作
- 专业复核：视为外部前置条件，需在上线前找儿科、营养、疫苗相关专业人士做一次轻审核

如果暂时没有稳定的专业复核资源，则建议：

- P1 先上线低风险内容
- 弱化或暂缓涉及疫苗、营养补充、异常判断的敏感段落
- 或进一步收缩为 `1-3 月龄` 的非敏感重点内容

结论：

> 在当前阶段，真正不能默认“你一个人全扛完”的，只有专业复核。

### 15.1 医疗风险

涉及：

- 黄疸
- 发热
- 疫苗
- 缺铁
- DHA
- 辅食
- 肠绞痛

这些内容不能写成诊断口吻，只能写成：

- 一般性育儿参考
- 常见现象说明
- 何时需要咨询医生 / 及时就医

### 15.2 信息过载

如果一口气塞太多，会破坏产品原本“轻记录”的气质。

所以必须控制：

- 首页只放摘要
- 正文每个分区尽量短
- 不做长文堆砌

### 15.3 内容可信度

建议所有正式上线内容至少满足：

- 有明确整理来源
- 有更新时间
- 有审核人或审核状态
- 敏感内容有免责声明

## 16. 推荐的内容策略

### 16.1 第一批内容来源

第一批可以以用户提供的月龄素材为灵感来源，但不建议直接照搬原文。

更稳妥的方式是：

- 提炼结构
- 重新编写为适合产品内阅读的短内容
- 对医学、营养、疫苗相关部分做专业复核

### 16.1.1 内容责任建议

建议至少明确这 3 个角色：

- 内容起草：负责把原始资料整理成产品内短内容
- 产品编辑：负责统一语气、长度、信息层级和跳转动作
- 专业复核：负责审看医学、营养、疫苗、异常提示等敏感表述

如果现阶段没有稳定复核资源，建议先缩到 `1-3 月龄`，不要一次铺开 `1-6 月龄`。

### 16.1.2 内容准备里程碑建议

建议不要让内容准备和开发工作完全并行无约束地推进，而是单独设一个前置 milestone：

- `Milestone A：内容准备`

完成标准建议为：

1. 明确首批覆盖月龄范围
2. 完成首批文案草稿
3. 完成产品编辑统一
4. 完成专业复核或确认敏感内容删减方案
5. 冻结第一批上线内容版本

只有这个里程碑完成后，再进入正式的 P1 上线排期，会更稳。

### 16.2 第一批覆盖范围

理想覆盖范围是：

- 1月龄
- 2月龄
- 3月龄
- 4月龄
- 5月龄
- 6月龄

这是最容易体现价值的一段时期，也是记录和焦虑最高频的一段时期。

但如果第一期内容生产与专业复核资源不足，建议先上线：

- 1月龄
- 2月龄
- 3月龄

先把前三个月的表达口径、用户反馈和修订流程跑顺，再扩展到 `4-6 月龄`。

### 16.3 内容颗粒度

每个月龄控制在：

- 1 个主题标题
- 3-5 条重点
- 2-4 条行动建议
- 1 组风险提示
- 2-4 个跳转动作

## 17. 推荐实施顺序

### P0：方案确认

- 确认是否认同“轻科普，不做内容流”的方向
- 确认第一期覆盖范围是 `1-6 月龄` 还是先收缩到 `1-3 月龄`
- 确认首页作为主入口
- 确认内容生产责任人和复核责任人
- 确认多宝宝场景下跟随“当前选中宝宝”展示
- 确认是否采用远程 JSON 配置作为第一期内容载体
- 确认远程失败时采用“本地最近成功快照优先，基础版内容兜底”的降级策略
- 确认是否为内容准备单独设置前置 milestone

### P1：最小可用版

- 首页卡片
- 月龄详情页
- 轻配置内容加载方案
- 多宝宝绑定逻辑
- 本地缓存快照兜底逻辑

### P2：体验增强

- 疫苗页轻提示
- 成长页联动提示
- 记录页场景知识插片
- 上下月龄切换
- 家庭成员共享查看

### P3：内容系统化

- 后端内容表
- 审核机制
- 后台维护
- 更多专题扩展

## 18. 我建议的最终方向

如果目标是“先做一个能明显提升产品价值、但又不把项目做重”的版本，我建议采用这条路径：

1. 不新增底部主导航 Tab
2. 首页加 `本月龄重点`
3. 做一个月龄详情页
4. 第一版优先做 `1-6 月龄`，但在内容资源不足时果断收缩为 `1-3 月龄`
5. 内容尽量短，并且强绑定记录、成长、疫苗入口
6. P1 先不做分散式场景插片，统一留到 P2
7. 医疗敏感内容统一加边界说明
8. 优先采用远程 JSON 轻配置，降低内容修复成本

这样最符合当前产品形态，也最容易低风险验证。

## 19. 待你 review 的关键决策点

这几个点最值得你拍板：

1. 功能定位是否接受：`轻科普 + 强联动`，而不是独立内容频道
2. 首页是否作为主入口
3. 第一阶段是做 `1-6 月龄`，还是先收缩到 `1-3 月龄`
4. 第一版内容载体是“远程 JSON 轻配置”还是“纯前端静态配置”
